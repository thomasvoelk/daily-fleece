# MongoDB JSON Schema validators and migrations as a separate deployment step

Each collection (`players`, `sessions`) is created with a `$jsonSchema` validator: `validationAction: error`, `validationLevel: strict`, `additionalProperties: false`, with `required` fields and per-field `bsonType` / `minLength` / `enum` constraints. The database itself rejects malformed writes regardless of which component issues them. Application-level validation (Bean Validation, domain guards) is not enough: it cannot protect against direct shell writes, future migration scripts, or any path that bypasses the domain layer.

**Migrations run as a separate pre-deployment step, not at application startup.** Embedding a migration runner (Mongock, Flyway, Liquibase) in the application process creates a class of problems described in [Keep your database deploys separate](https://www.philandstuff.com/2018/04/04/keep-database-deploys-separate.html): rolling deploys have multiple instances competing to apply the same migration; a slow migration blocks health-check readiness; and a migration failure prevents the application from starting at all, conflating two failure modes — bad schema and bad code — that have different owners and different remediation paths. See also [Database Migrations in the Real World](https://blog.jetbrains.com/idea/2025/02/database-migrations-in-the-real-world/) for a broader survey of the trade-offs. Migration scripts are `mongosh` JavaScript files in `src/main/resources/db/migration/` run via the Flyway Native Connectors CLI before each deploy.

**Integration test setup uses the Java MongoDB driver, not `mongosh`.** Migrations are applied inside the Testcontainers MongoDB container via a temporary `MongoClient` created from `container.getConnectionString()` and closed immediately after. A sidecar `GenericContainer` running `mongosh` was tried first but is unreliable: Testcontainers' `Wait.forLogMessage` on a short-lived container can return before the command actually completes, silently skipping migrations. `execInContainer` is synchronous and returns an exit code, but still requires `mongosh` to be present in the image at a known path. The Java driver needs no binary, throws on failure, and runs in the same JVM. The database name is derived from the container's connection string rather than hardcoded because Spring Boot's `@ServiceConnection` appends `/test` to the MongoDB container URI, overriding `spring.data.mongodb.database`.

**`_class` suppression.** Spring Data MongoDB writes a `_class` discriminator field by default; `additionalProperties: false` causes every write to fail. `MongoConfig` overrides the auto-configured `MappingMongoConverter` bean and sets `DefaultMongoTypeMapper(null)`. Registering a `MongoTypeMapper` bean alone has no effect in Spring Boot 3.x — the auto-configured converter does not take it as a constructor dependency.

## Considered options

- **`validationAction: warn`** — rejected: silent failures give a false sense of safety and delay detection; fail fast is the right default.
- **Mongock** — rejected: in-process migration runner with the same rolling-deploy and lifecycle-coupling problems as embedded Flyway.
- **`execInContainer` for test migrations** — rejected: `Wait.forLogMessage` on a short-lived container is unreliable; Java driver is simpler and fully synchronous.
